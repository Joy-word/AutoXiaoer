# 决策模型使用方案

**版本：** V1 讨论稿（2026-10-14）

**目标：** 使用低延迟决策模型减少 LLMAgent 的查询往返，并为多任务调度、候选排序和任务状态分类提供建议，同时保持最终规划、权限控制和设备操作由现有系统负责。

**范围：** 本文是架构讨论记录，不代表已经实现。本阶段不修改业务代码；具体模型、部署方式、接口和校准方法后续确定。

---

## 1. 核心定位

决策模型适合做低延迟的：

- 分类。
- 多标签匹配。
- 候选排序。
- 查询结果筛选。
- 任务关系判断。
- 调度建议。

决策模型不承担完整的自然语言规划，也不直接拥有手机操作、队列修改、流程发布或记忆写入权限。

建议职责边界：

> 决策模型负责快速判断和提出建议；LLMAgent 负责语义规划与工具调用；程序负责权限、状态一致性、设备互斥和不可逆操作保护。

---

## 2. 首要用途：减少查询步骤

当前工具目录会一次性提供给 LLMAgent，因此不需要让决策模型决定“应该调用哪个工具”。它的主要价值是减少查询类工具的往返：

```text
任务上下文
    → 决策模型批量筛选候选
    → 将候选 ID、路径和评分提供给 LLMAgent
    → LLMAgent 按需读取具体内容
    → LLMAgent 继续规划和执行
```

候选内容不直接替代工具结果。决策模型只提供索引和排序，LLMAgent 仍需通过正式工具读取完整内容。

### 2.1 经验记忆推荐

当前项目的 [MemoryTools.kt] 中已有 `read_memory_index` 和 `read_memory_file`。决策模型可以根据任务、应用、当前页面和最近执行结果，批量筛选相关记忆：

```json
{
  "memories": [
    {
      "path": "apps/支付宝/蚂蚁庄园.md",
      "score": 0.91,
      "reason": "包含蚂蚁庄园入口、捐蛋页面和已知等待时间"
    }
  ]
}
```

LLMAgent 获得候选后，再调用：

```text
read_memory_file(path = "apps/支付宝/蚂蚁庄园.md")
```

`read_memory_index` 保留为兜底工具。决策模型不可用、候选不充分或 LLMAgent 认为需要全量索引时，仍可主动读取索引。

### 2.2 流程候选筛选

决策模型可以返回相关流程的 ID、描述摘要和评分，避免 LLMAgent 先读取全部流程目录：

```json
{
  "workflows": [
    {
      "id": "ant_manor_collect_eggs",
      "score": 0.86
    },
    {
      "id": "ant_manor_donate_eggs",
      "score": 0.72
    }
  ]
}
```

评分表示“是否值得提供给 LLMAgent 参考”，不是当前可执行性，也不是业务成功概率。LLMAgent 仍需检查前置条件，执行器仍需完整校验 JSON。

### 2.3 历史和异常记录排序

同一机制可以筛选：

- 相似任务历史。
- 相关流程失败记录。
- 与当前页面相关的异常处理经验。
- 可能解释当前问题的历史证据。

决策模型只返回记录 ID 或文件路径；完整历史内容由正式读取工具获取。

---

## 3. 一次性多问题决策

决策模型支持一次请求评估多个独立问题，可以将查询筛选集中在同一轮：

```json
{
  "memoryCandidates": [
    { "path": "apps/支付宝/蚂蚁庄园.md", "score": 0.91 }
  ],
  "workflowCandidates": [
    { "id": "ant_manor_collect_eggs", "score": 0.86 }
  ],
  "historyCandidates": [
    { "id": "history-123", "score": 0.74 }
  ],
  "taskRelation": {
    "type": "independent",
    "score": 0.88
  }
}
```

第一版应保持输出类别有限，避免把一个“快速决策接口”扩展成新的通用 Agent。建议优先支持经验记忆、流程和历史候选三类查询。

### 3.1 分数规则

- 每个候选独立评分，允许多个候选同时超过阈值。
- 初始筛选条件可采用 `score > 0.5`，但这是相关性阈值，不是成功概率承诺。
- 允许零候选，不强制返回一个结果。
- 命中后按分数排序，并设置最大候选数量和总上下文预算。
- 如果接口只返回候选之间总和为 1 的互斥 Softmax，不应直接把结果当成独立相关性概率使用。
- 没有项目数据校准前，应记录实际采用率、漏召回和误召回，后续调整阈值。

## 4. 并发任务调度建议

当多个任务同时进入时，决策模型可以判断任务之间的关系，并建议排队、合并或在安全检查点插入。

```text
新任务进入
    → 决策模型判断任务关系和紧急性
    → 程序检查设备状态和安全边界
    → 排队、检查点插入、合并、拒绝或请求用户决定
    → TaskExecutionManager 执行确定的调度结果
```

建议输出：

```json
{
  "decision": "interrupt_at_checkpoint",
  "taskId": "task-new",
  "score": 0.91,
  "reason": "当前任务正在执行不可重复的捐赠操作，新任务应等待当前检查点"
}
```

可用决策：

- `queue`：进入等待队列。
- `interrupt_at_checkpoint`：当前任务到达安全检查点后插入。
- `merge`：与已有任务合并，复用相同导航或页面读取。
- `reject`：无法执行或资源／权限不满足。
- `ask_user`：模型无法安全决定，需要用户选择。

决策模型不能直接修改队列。最终结果必须由程序验证：

- 当前动作是否可中断。
- 是否已经进入捐赠、支付、删除等不可重复或不可逆区间。
- 两个任务是否使用同一设备、同一应用或互相影响的页面状态。
- 当前任务是否处于等待、暂停、PhoneAgent 导航或流程执行中。
- 插入任务是否需要保存当前屏幕和恢复点。
- 当前任务结束后能否可靠恢复原页面和流程边界。

当前项目的 [TaskExecutionManager] 继续作为队列和控制的唯一执行入口；决策模型只提供调度建议。

### 4.1 任务合并的限制

以下情况可以考虑合并：

- 多个任务共享同一应用启动和导航过程。
- 多个任务只是读取同一页面的不同信息。
- 合并不会改变用户意图和结果解释。

以下情况不应自动合并：

- 涉及不同账号、权限或用户确认。
- 包含捐赠、支付、删除、发送等副作用操作。
- 一个任务失败会改变另一个任务的结果。
- 任务需要不同的设备或应用状态。

## 5. 其他适合场景

### 5.1 任务是否值得优先使用流程

快速判断当前任务是否可能存在稳定、短小、低风险的固定片段：

- 适合先查询流程。
- 适合直接交给 PhoneAgent。
- 需要先获取更多页面证据。

这可以减少 LLMAgent 反复查询流程后再放弃的步骤，但不能替代流程 JSON 的完整校验。

### 5.2 任务阶段分类

根据任务输入、最近工具调用和结果，判断粗粒度阶段：

- `navigation`：仍在导航。
- `arrived_at_target_page`：已到目标页面。
- `ready_for_workflow`：可能适合执行固定流程。
- `verification`：需要核实业务结果。
- `recovery`：发生异常，需要 PhoneAgent 接管。
- `waiting_user`：等待用户输入或确认。

该分类用于减少重复分析，不作为手机动作授权。

### 5.3 失败类型和流程修订触发

流程失败后，可快速分类：

- JSON 格式或字段错误。
- 执行器不支持动作。
- 页面布局或应用状态变化。
- 前置条件不满足。
- 临时网络问题。
- 业务结果不明。
- PhoneAgent 成功恢复，值得修订。

该结果可以决定是否创建 WorkflowAgent 整理作业，但不能直接修改流程 JSON。缺少成功证据时，不应触发自动修订或覆盖。

### 5.4 经验记忆写入候选

任务完成后，决策模型可以判断：

- 是否产生了稳定的新经验。
- 应更新已有记忆还是创建新记忆。
- 哪些内容只是临时状态，不应写入长期记忆。
- 是否包含需要脱敏的账号、联系人或隐私信息。

最终写入仍由 WorkflowAgent 或 LLMAgent 通过现有记忆工具完成，决策模型不直接写文件。

### 5.5 用户交互和通知优先级

多个任务同时需要用户处理时，可以判断：

- 哪个请求更紧急。
- 是否能合并成一次询问。
- 哪些任务可以继续排队。
- 哪些结果需要立即通知。

该能力不能绕过暂停、停止、权限和用户确认机制。

---

## 6. 不适合交给决策模型的职责

以下行为必须由程序或 LLMAgent 保持控制：

- 直接执行手机动作。
- 直接确认支付、捐赠、删除或发送等不可逆操作。
- 直接修改任务队列。
- 直接覆盖流程 JSON 或记忆文件。
- 判断点击是否已经产生业务成功。
- 绕过权限、用户确认、暂停和取消机制。
- 在结果不明时决定安全重试。
- 在没有证据时宣称流程成功或修订有效。

决策模型输出任何建议，都应视为不可信的业务输入，经过结构化解析、白名单校验和确定性规则兜底。

---

## 7. 推荐的调用时机

### 查询筛选

在 LLMAgent 即将执行查询类工具之前，如果当前已有任务上下文和候选目录，可以先调用决策模型筛选候选。LLMAgent 读取命中的具体内容，而不是先读取全量索引。

### 规划轮次

如果需要根据最新执行结果刷新候选，应在：

```text
ToolResult 加入 LLMAgent 上下文
    → 收集本轮用户指导
    → 决策模型批量评分候选
    → 更新可替换的推荐块
    → 发起下一次 LLMAgent 请求
```

推荐块每轮替换，不累计追加。决策模型失败或超时则清除过期推荐，继续原有 LLMAgent 和 PhoneAgent 路径。

### 新任务进入

在任务真正加入队列前调用一次并发关系判断。若当前任务正在不可中断区间，程序应直接拒绝立即插入建议，改为等待安全检查点；不需要等待决策模型再次确认。

## 8. 数据输入和缓存

决策模型输入由程序组装，不再额外调用 LLM 生成摘要。可包含：

- 原始任务描述。
- 最新计划和有限数量的最近工具记录。
- 有来源的当前页面和应用状态。
- 本轮用户指导。
- 候选项的 ID、路径、描述和必要元信息。
- 当前设备、前台应用和任务队列摘要。

未知值必须显式表示未知，不能由程序猜测。

缓存键应覆盖：

- 任务上下文。
- 用户指导。
- 最近工具结果。
- 候选目录及其内容修订。
- 当前队列状态。
- 模型版本和评分配置。

流程覆盖、记忆写入、候选删除或任务状态变化后，相关缓存必须失效。推荐结果不能作为执行授权，执行时仍需重新读取和校验当前对象。

---

## 9. 失败降级和观测

- 决策模型超时：跳过推荐，继续主流程。
- 服务不可用：保留主动查询和现有 PhoneAgent 回退。
- 返回格式错误：丢弃本次结果，不执行模型返回的任何动作建议。
- 分数缺失、越界或非数字：丢弃对应候选。
- 推荐结果为空：清除旧推荐，不保留过期候选。
- 任务取消：取消未完成的决策请求，不阻塞任务结束。
- 模型建议与程序安全规则冲突：以程序规则为准。

应记录：

- 请求类型和输入摘要哈希。
- 模型版本、耗时和返回状态。
- 命中候选及评分。
- LLMAgent 实际读取和采用的候选。
- 漏召回、误召回和后续任务结果。
- 调度建议与程序最终决策的差异。

日志中不得保存不必要的完整聊天内容、截图或敏感记忆正文。

---

## 10. V1 建议优先级

1. 经验记忆、流程和历史候选的批量筛选。
2. 查询步骤减少和候选排序。
3. 并发任务的排队、检查点插入和合并建议。
4. 任务阶段和失败类型分类。
5. WorkflowAgent 整理触发建议。
6. 经验记忆写入候选和通知优先级。

第一阶段不实现复杂自主调度，不允许决策模型直接改变队列或执行手机动作。

---

## 11. 待继续确认

1. 决策模型的具体实现：本地模型、远程服务、模型大小和 Android 端运行方式。
2. 多问题请求的统一输入／输出协议，以及候选类型的版本管理。
3. 相关性分数的校准数据、阈值、候选数量和上下文预算。
4. 任务安全边界：哪些现有动作属于可插入点，哪些动作属于不可中断区间。
5. `merge` 任务的结果归属、失败传播和恢复策略。
6. 并发任务的优先级、用户紧急指令和现有队列优先级如何合并。
7. 记忆候选与流程候选是否共享一次评分请求，及隐私数据的发送范围。
8. 决策日志、缓存和候选证据的保留时间。

这些问题确定前，不应把决策模型扩展为自动执行器或队列控制器。
